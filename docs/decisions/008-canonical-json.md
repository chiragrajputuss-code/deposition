# 008 — Canonical JSON moves to RFC 8785, schema becomes v1

**Status:** proposed, awaiting decision · **Date:** 2026-10-01
**Raised by:** an attempt to verify a trace in a browser

## The problem

Schema v0's hash input is Python's serialiser:

```python
json.dumps(sort_keys=True, separators=(",", ":"), ensure_ascii=False, allow_nan=False)
```

[ADR 002](002-schema-v0.md) calls that byte-level contract "the guarantee". It is
not a contract any other language can keep.

Measured on a real trace from `examples/04_refund_dispute.py`, the `decision`
event at seq 3:

```
python canonical : {"body":{"approved_usd":50.0,"detail":"outside 30-day window…
python sha256    : 1adfbcb5eb3fc206a1dcc6451e21243f35bf71337e36af7b4c9a2415789b0aba
stored hash      : 1adfbcb5eb3fc206a1dcc6451e21243f35bf71337e36af7b4c9a2415789b0aba

js canonical     : {"body":{"approved_usd":50,"detail":"outside 30-day window…
js sha256        : a04ccc3dbdcf2964b66cf64871dd596c4f193e3e5fab0cdfc1898486f75b55e0
```

Python writes `50.0`. JavaScript writes `50`. Different bytes, different hash.
The difference is not a bug in either language — JSON has no canonical number
form, so every runtime picks one.

**An independent verifier written in JavaScript, Go, Java or Rust computes a
different hash and concludes the trace was tampered with.** Offline verification
by a third party only works if the third party runs Python with the same `json`
module, which is not what "a record you can show to someone who does not trust
you" means. The claim in the README is currently false outside this SDK.

Two things sharpen it. The IETF draft for agent audit trails
(`draft-sharif-agent-audit-trail`) specifies SHA-256 chaining **per RFC 8785**,
so the field is converging on a canonicalisation that v0 does not implement. And
browser-side verification — handing a regulator one HTML file that checks the
trace with no server and no reason to trust us — is impossible to build on v0.

## Decision

Adopt **RFC 8785 (JSON Canonicalization Scheme)** as the hash input, and bump the
schema `v` field from `0.1` to `1.0`.

Verified before proposing: with RFC 8785 number formatting, Python and Node
produce byte-identical output and the same SHA-256 for the event above
(`a04ccc3d…`).

### What actually changes

1. **Numbers** serialise per ECMAScript `Number::toString` rather than Python
   `repr`. In practice: an integral float loses its `.0` (`50.0` → `50`), and
   large or small magnitudes follow ECMAScript's exponent rules rather than
   Python's. Non-finite values stay rejected, as now.
2. **Keys** sort by UTF-16 code unit rather than Unicode code point. Identical for
   ASCII; different only for keys containing non-BMP characters, which body keys
   can carry because they come from user data.

String escaping already matches: Python's short forms (`\n`, `\t`, `\"`, `\\`) and
`\u00XX` for other control characters are what JCS requires, and
`ensure_ascii=False` already emits UTF-8 directly.

### What does not change

The event shape, the field names, the chain rules, the genesis hash, the
signature sidecar format, the blob threshold and the CLI contract are all
untouched. This is a change to one function's output bytes, and to the `v` field
that declares which function was used.

### Migration

The writer emits `v1` only. **The verifier dispatches on the event's own `v`
field** and keeps the v0 serialiser for reading, so no trace that exists ever
becomes unverifiable. That costs about ten lines and avoids the one outcome an
evidence product must never produce: a record its own tool can no longer check.

v0 traces stay verifiable in Python and remain unverifiable anywhere else. That
is a property of those traces, not something a later version can repair, and the
documentation should say so rather than imply the fix was retroactive.

### Why now

Nothing is published. There is no git remote, the package is not on PyPI, and
every v0 trace in existence was generated by us while testing. The migration cost
today is `rm -rf ./deposition`.

The moment one real run is recorded — a signed refund trace sitting in a
chargeback file — that cost becomes a migration path maintained forever, for a
defect that invalidates the product's central claim. The cost of this change only
rises, and it rises on the first user.

## Alternatives rejected

**Keep Python canonicalisation and ship verifiers in each language.** Every
verifier would have to replicate Python's float `repr` exactly, including its
exponent thresholds. That is a permanent, silent correctness liability in code we
do not control, to preserve a format nobody else chose.

**Hash the stored line as written.** Appealing, because the bytes on disk are
unambiguous. It does not work: the hash covers the event *without* its `hash`
field, so recomputing it means re-serialising the rest, which is the problem
again. Extracting one key from a serialised string is string surgery on
evidence — worse than the disease.

**Adopt the IETF draft's whole event format, not just its canonicalisation.** Out
of scope here, and premature: the draft is an individual submission rather than a
working-group document, and it carries an IPR disclosure that needs reading before
anything of ours conforms to it. Matching its canonicalisation costs nothing and
keeps that option open.

## Consequences

- Every event hash changes. Fixtures, doctests and any committed example output
  are regenerated in the same commit.
- `schema.py` and `chain.py` both change, so per the standing rules this ships
  with tests in the same commit. The tests must include **cross-language
  vectors**: a pinned set of events whose canonical bytes and hashes are asserted
  in Python and re-checked by Node in CI, including integral floats, exponent
  edges, non-ASCII keys and nested structures. Without that, this regresses
  silently the first time someone touches the serialiser.
- A `deposition verify` run on a v0 trace must say, in words, that the trace
  predates RFC 8785 canonicalisation and can only be verified by this SDK.
- The self-verifying single-file viewer becomes buildable, and should be, because
  it is the demonstration this whole change exists to enable.
- Marketing may not claim "independently verifiable" until the Node cross-check
  is green in CI. Until then the honest phrasing is "verifiable with the
  Deposition CLI".
